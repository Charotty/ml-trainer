# CT Workbench UI — требуемые улучшения

Документ фиксирует результаты ревью MVP-интерфейса (`frontend/public/`) от 2026-07-10.  
Связанные документы: [PRD.md](PRD.md), [FEATURES_AND_SCENARIOS.md](FEATURES_AND_SCENARIOS.md), [ARCHITECTURE.md](ARCHITECTURE.md).

**Текущая оценка:** практичность 6/10 (инженерный MVP), качество прототипа 7/10.

---

## 1. Цели улучшений

| Цель | Описание |
|------|----------|
| G-UI-01 | Сделать интерфейс пригодным для врача (не только для инженера) |
| G-UI-02 | Снизить ошибки пользователя на длинном сценарии (upload → extraction → QA → predict) |
| G-UI-03 | Улучшить обратную связь при async-операциях (минуты на extraction) |
| G-UI-04 | Выровнять UI с roadmap из PRD (F-xxx, US-xx) |

## 2. Критичные улучшения (P0)

### UI-P0-01 — DICOM viewer с оверлеями

| Поле | Значение |
|------|----------|
| **Проблема** | QA по координатам «вслепую» без срезов КТ непригоден для клиники |
| **Требование** | Просмотр аксиальных/сагиттальных/корональных срезов; overlay масок почек/позвоночника; клик по срезу обновляет координаты в QA |
| **Связь** | F-016, US-02 |
| **Приоритет фазы** | v1.1 |
| **Критерий готовности** | Врач может визуально проверить центр почки и сохранить правку без внешнего PACS |

### UI-P0-02 — Человекочитаемые подписи полей QA

| Поле | Значение |
|------|----------|
| **Проблема** | Технические имена (`kidney_left_center_x_rel`) непонятны врачу |
| **Требование** | Отображать русские подписи + единицы (мм); техническое имя — tooltip или вторичный текст |
| **Пример** | `kidney_left_center_x_rel` → «Левая почка, X (медиолатеральная), мм» |
| **Связь** | F-005, US-02 |
| **Приоритет фазы** | v1.1 (минимальный словарь — можно в MVP+) |
| **Критерий готовности** | Все 17 полей QA имеют русскую подпись и единицу измерения |

### UI-P0-03 — Dashboard кейсов на первом экране

| Поле | Значение |
|------|----------|
| **Проблема** | Список кейсов внизу длинной страницы; неудобно при нескольких пациентах |
| **Требование** | Отдельный экран/вкладка «Кейсы» — первая точка входа; таблица: id, метка, status, coverage, дата |
| **Связь** | F-011, US-01, US-05 |
| **Приоритет фазы** | v1.1 |
| **Критерий готовности** | Пользователь открывает приложение и сразу видит список кейсов + «Новый кейс» |

## 3. Важные улучшения UX (P1)

### UI-P1-01 — Пошаговый wizard / вкладки

| Поле | Значение |
|------|----------|
| **Проблема** | Один длинный скролл; шаги 4–6 видны до завершения extraction |
| **Требование** | Wizard: Upload → Analyze → QA → Predict → Report; шаги 4+ скрыты до `features_ready` |
| **Связь** | US-01 |
| **Критерий готовности** | На шаге Upload не отображаются пустые поля QA |

### UI-P1-02 — Inline-ошибки и уведомления (без alert)

| Поле | Значение |
|------|----------|
| **Проблема** | `alert()` для успеха/ошибок; необработанные исключения в обработчиках кнопок |
| **Требование** | Toast или banner для success/error; `try/catch` на все API-вызовы; показ `detail` от FastAPI |
| **Критерий готовности** | Ни одного `alert()`; ошибка upload/predict видна в UI |

### UI-P1-03 — Loading-состояния кнопок

| Поле | Значение |
|------|----------|
| **Проблема** | Неясно, идёт ли запрос при Upload / Save QA / Predict |
| **Требование** | Disable + spinner/текст «Загрузка…» на время запроса |
| **Критерий готовности** | Двойной клик по Predict не отправляет два запроса |

### UI-P1-04 — Загрузка прогноза при открытии кейса

| Поле | Значение |
|------|----------|
| **Проблема** | «Открыть» кейс со статусом `predicted` не показывает таблицу Δ |
| **Требование** | При открытии кейса подгружать `features` + `prediction.json` (если есть) |
| **Связь** | US-03 |
| **Критерий готовности** | Открытый predicted-кейс сразу показывает 6 значений смещения |

### UI-P1-05 — Coverage с цветовой индикацией

| Поле | Значение |
|------|----------|
| **Проблема** | Coverage только текстом; нет предупреждения перед прогнозом |
| **Требование** | Badge: ≥90% зелёный, 80–90% жёлтый, &lt;80% красный; список `missing_features` раскрываемый |
| **Связь** | F-007, F-009, US-07, NFR-008 |
| **Критерий готовности** | При coverage &lt;80% — явный warning перед кнопкой «Прогноз» |

### UI-P1-06 — Группировка полей QA

| Поле | Значение |
|------|----------|
| **Проблема** | 17 полей в одной сетке без структуры |
| **Требование** | Подсекции: «Левая почка», «Правая почка», «Позвоночник», «Центр масс тела», «Размеры тела», «Объёмы» |
| **Связь** | F-005 |
| **Критерий готовности** | Поля сгруппированы визуально с заголовками секций |

### UI-P1-07 — Улучшенный progress extraction

| Поле | Значение |
|------|----------|
| **Проблема** | Progress bar есть, но нет отмены и оценки времени |
| **Требование** | Показывать `stage` + `message` человекочитаемо; опционально «~N мин»; кнопка «Отмена» (если backend поддержит) |
| **Связь** | F-003, US-01 |
| **Критерий готовности** | При `failed` — текст ошибки в карточке, не только в консоли |

## 6. Технический долг фронтенда

| ID | Проблема | Требование |
|----|----------|------------|
| TD-01 | Монолитный `app.js` | Разбить на модули: `api.js`, `cases.js`, `qa.js`, `ui.js` |
| TD-02 | Нет TypeScript | При выборе стека — миграция на TS + типы API |
| TD-03 | Нет тестов UI | E2E (Playwright) на сценарий US-01 с mock API |
| TD-04 | Смешение RU/EN в UI | Единый словарь i18n (`ru.json`) |
| TD-05 | `readQaOverrides` шлёт все заполненные поля | Отправлять только изменённые поля (dirty tracking) |
| TD-06 | Нет валидации чисел в QA | Min/max, NaN-check, подсветка невалидных полей |
